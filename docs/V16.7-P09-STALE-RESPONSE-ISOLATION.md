## P0 #9 requirements — status

### Requirement: Every in-flight consult is bound to profileId, conversation/session generation id, and request identity; verified immediately before applying (not just at dispatch)

**Implemented in `pi/extensions/ues.ts` (consult dispatch site, ~lines 6601–6630) and hardened by the generation identity in `lib/deepseek-session-budget.mjs`:**

- Immediately before `const consultation = turnsAllowed && !cacheLookup.cached ? await webLane.consult({...}) : null;`, a `dispatchedContext` object is captured with:
  - `profileId` — the OPAQUE crypto-random registry profile id (`resolveDeepSeekProfileId(process.env, cwd)`), delegated to the registry in the P0 #1/P0 #6 checkpoint edits.
  - `sessionId` — the current `deepSeekSession?.id` (the run-scoped conversation identity).
  - `generationId` — the **authoritative generation discriminator**: a fresh UUID (`gen-<12 hex>`) emitted on every `createConversationSession` (initial session **and** rotation successor). Per the P0 #9 hardening, the session id alone is not relied upon for generation distinction, so a stale result can never be re-attached to a rotated conversation or a re-authenticated run.
  - `traceId` — the run trace id (`<prefix>-<ISO-timestamp>-<random8>`), unique and never reused per run.
  - `consultId` — a fresh `crypto.randomUUID()` binding this dispatch to exactly one result.
- The request identity flows into the consult input: `requestId: dispatchedContext.consultId`.

### Requirement: Discard stale responses — no conversation attach, no evidence update, no cache write, no budget consume/restore, no auth-state change, no task resumption

**Implemented as the "stale-check" block (~lines 6630–6685):**

Immediately before any result is committed (cache put, `recordDeepSeekTurn`, learner samples, advisor recording), the five identities are re-verified:

1. `consultation.requestId !== dispatchedContext.consultId` → **request-identity-mismatch**
2. `resolveDeepSeekProfileId(process.env, cwd) !== dispatchedContext.profileId` → **profile-switched** (Case A)
3. `(deepSeekSession?.id ?? null) !== dispatchedContext.sessionId` → **conversation-rotated** (generation id changed)
4. `(deepSeekSession?.generationId ?? null) !== dispatchedContext.generationId` → **generation-identity-changed**
5. `dispatchedContext.traceId !== traceID` → **trace-mismatch**

On any mismatch:
- A run-journal event `v16.7.deepseek.stale-response-discarded` is appended with full provenance (dispatch vs. arrival profile/session/generation/request ids + deterministic reason).
- `webLane.undoConsultation()` rolls back the reservation only (see budget-rollback audit below).
- `pendingResumeCapsuleText = ""` so the discarded consult's resume text cannot leak into the next consult.
- `consultation = null` — the result is DISCARDED: nothing below commits it (no `recordDeepSeekTurn`, no `deepSeekCache.put`, no learner sample, no advisor recording, no auth-state change, no task resumption).

### Requirement: Case A (profile switch) and Case B (re-auth → generation rotate) handling via generation identity

Handled explicitly with distinct journal `reason` values (`profile-switched`, `conversation-rotated`, `generation-identity-changed`), each fail-closed (result discarded, never replayed or resumed). Profile change is caught by the opaque `profileId`; the new `generationId` guarantees that a profile's own new generation (same account, post-re-auth or post-context-reset) cannot absorb an old result even when the profile id matches.

## Audit #1 — `undoConsultation()` budget rollback semantics

**Question:** does discarding a stale consult leak global budget, refill an unlimited-retry loop, or corrupt turn accounting?

**Answer: no leak. The reservation model is correct.**

- **Where budget is consumed:** in `lib/web-reasoning-lane.mjs#consult()`, the lane first enforces the ceiling (`state.consultations >= maxConsultations` → `budget-exhausted` skip), then reserves: `state.consultations += 1`. `maxConsultations` = `WEB_LANE_LIMIT.defaultMaxConsultations` (default 1), a **lane-local, per-run** bounded counter, **not** wired to any global DeepSeek session budget.
- **Where the reservation is refunded:** `undoConsultation()` (lane line 184) decrements `state.consultations = Math.max(0, state.consultations - 1)`.
- **Where a turn is COMMITTED (irreversible):** only in the non-stale branch of the guard, `recordDeepSeekTurn("consult", consultation, false)` — which increments `deepSeek.turnsUsed`, `deepSeek.consultations`, `cacheMisses`, records a session budget turn, and may trigger session rotation. **On stale discard, `recordDeepSeekTurn` is never reached** — the `if (staleConsultation)` block does `undoConsultation()` and `consultation = null`, then skips the whole else-branch. So no committed turn, no `recordSessionTurn`, no rotation trigger, no cache miss accounting, no auth-state change.
- **Loophole analysis:** the reservation model (consume at dispatch, refund on discard) is the intended architecture: only accepted results commit. A discarded consult nets **zero** budget consumption. A subsequent retry consumes a *fresh* reservation from a fresh dispatch and is refunded independently if it also discards. There is no cumulative refill and no budget grow: the lane ceiling and the per-run `deepSeek.turnBudget` (8 turns max) remain the hard bounds, and `undoConsultation` floors at 0. Discarding therefore cannot extend the effective budget beyond what a successful consult would have cost.
- **Cross-check in `pi/extensions/ues.ts`:** `recordDeepSeekTurn` also guards `deepSeek.turnBudget` before recording and `deepSeek.cacheHits += 1` / `cacheMisses += 1` are untouched by the discard path. The discard path touches no `sessionBudget.recordSessionTurn`, no rotation, no `pendingResumeCapsuleText` beyond clearing it.

**Verdict:** `undoConsultation()` performs a clean, reservation-only rollback. No global budget refill, no unlimited-retry loophole, no turn-accounting corruption.

## Audit #2 — A → B → A profile-switch race and re-auth generation race

**Question:** does `deepSeekSession.id` act as a true generation identity (A1 ≠ A2), and does the guard hold without relying solely on `requestId`?

**Trace of the identity source (ues.ts ~line 6220 → session-budget):**
- `createConversationSession` now emits a fresh `generationId = gen-<random12>` on **every** creation (initial session + rotation successor). This is the authoritative generation discriminator.
- `deepSeekSession.id` is `ues-${traceID}` (production override), with rotations producing `ues-${traceID}#1`, `#2`, …
- `traceID = <prefix>-<ISO-timestamp>-<random8>` (`lib/trajectory.mjs#createTraceID`) — unique and never reused per run.

**Race analysis:**
- **Cross-run (profile A → B → A across runs):** each run gets a new traceID → new session id (`ues-T2`, `ues-T3`) → caught by `sessionId` and `traceId` checks; `generationId` also differs.
- **Within a run, rotation:** `rotateConversationSession` builds a successor session via `createConversationSession` → new `generationId` and `ues-T#N` id → caught by both checks.
- **Within a run, same session (profile is worker-bound, so no mid-run profile switch is possible):** only one consult dispatch occurs (`attempt === 1`), so only the `requestId` could match — but the `generationId` check is now present, making the guard independent of `requestId` uniqueness for the critical case.
- **A1 ≠ A2 is guaranteed by construction** via the per-creation `generationId`, so a return-to-profile-A after an interposed profile/B or re-auth **cannot** carry an old result.

**Verdict:** the guard is fail-closed with defense-in-depth: profile, session, generation, trace and request identities all re-verified immediately before commit; the `generationId` hardening removes the last theoretical reliance on `requestId` alone.
