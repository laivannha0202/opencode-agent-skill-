# V16.7 — DeepSeek Account, Profile & Authentication Lifecycle

V16.6.1 made the DeepSeek Web runtime *correct with one account*. V16.7 makes it
*safe with many*: independent profiles, an explicit active profile, a bounded
manual login, a read-only auth probe, and a mid-task expiry path that continues
the task without losing state — all without UES ever reading a password, cookie,
token or `storageState`, and without ever sending a credential to a model, a
prompt, the Evidence Store, Git, npm or telemetry.

## Why this release exists

Three failure modes motivated it, each observed in the V16.3–V16.6 line:

1. **One hard-coded profile.** `deepseek-web` was the only profile name. A user
   with a personal and a work account could not keep them apart, and switching
   meant logging out of one to log into the other.
2. **Silent wrong-account use.** A run that lost its login could quietly fall
   back to "whatever profile exists" and consult the wrong account's session.
3. **Mid-task expiry lost state.** When a session expired between turns, the run
   had no bounded, secret-free way to hand the task to the next attempt.

V16.7 fixes all three by making profiles explicit first-class objects, removing
every auto-fallback, and adding a credential-free Resume path for expiry.

## Non-negotiable safety contract

The following are asserted by `test/deepseek-profile-v16-7.test.mjs` (sections
E–F) and reported by `ues deepseek doctor`:

- UES **never** reads a cookie, token, `storageState`, password or credential.
- UES **never** prints or stores a credential, in state, telemetry or the
  Evidence Store.
- UES **never** autofills credentials, solves a CAPTCHA or injects an OTP.
- UES **never** copies a cookie or session between profiles.
- UES **never** auto-falls-back to another account or another profile.
- UES **never** grants DeepSeek filesystem, Git or terminal rights.
- Login is **manual**; the runtime opens a real browser window and waits.

## Profile registry (`lib/deepseek-profile-registry.mjs`)

A profile is metadata: an opaque id, a human name, a label and a state. There is
no field for a credential and no code path that opens a profile's cookie jar.

| Property | Behaviour |
| --- | --- |
| Location | `<ues-config>/browser-profiles/<name>` and `<root>/profiles.json`, **outside the repository** |
| Names | `^[a-z0-9][a-z0-9._-]{0,63}$`; `..`, separators and reserved names (`profiles.json`, `profiles.lock`) are rejected |
| Containment | the resolved directory must be strictly inside the profiles root |
| Writes | atomic (temp file + rename); no partial registry is ever observed |
| Corruption | a corrupt registry is **reported**, never silently repaired; mutating commands refuse |
| Active profile | **explicit**. No auto-fallback: a missing active profile resolves to `null` |
| Removing active | clears the active pointer; never promotes another profile |
| Limit | 32 profiles |

The **opaque profile id** (`pr-<24 hex>`) is derived from the name via SHA-256.
It carries no directory, path or name fragment, so it is safe to place in a
cache key or a telemetry row.

## Per-profile lock (`lib/deepseek-profile-lock.mjs`)

A persistent browser profile can be driven by exactly one process at a time.

- Exclusive atomic create (`wx`); racing processes cannot both win.
- Records owner pid, host, timestamps and a random token.
- A **stale** lock (TTL passed, or the owner pid is provably dead **on this
  host**) is reclaimed and the reclaim is reported, never silently ignored.
- A lock from another host is never stolen on liveness, only on TTL.
- Release is **token-safe**: a non-owner cannot remove a live lock.

## Auth lifecycle (`lib/deepseek-auth-lifecycle.mjs`)

Canonical states: `not-probed`, `ready`, `needs-auth`, `indeterminate`,
`expired`.

Classification is **fail-closed**. It wraps the existing V16.3
`classifyAuthState` evidence contract (`READY` requires a composer **and**
positive session evidence — an answer region, an account affordance, or ≥2
history rows). Any unrecognized state becomes `indeterminate`; nothing is ever
guessed to be logged in.

- `canContinueWithState` passes **only** `ready`.
- `authRecoveryPlan` names exactly one next action and always sets
  `substituteAccount: false`.
- `nextManualAuthWait` bounds the manual login by **both** probe count (90) and
  wall clock (180 s), and treats a closed/dead browser as terminal.
- A prior `ready` followed by a login wall is `expired` — the **mid-task**
  signal — which yields `expiryResumeRequest`, a credential-free request the
  caller feeds to the existing bounded Resume Capsule.

## Profile doctor (`lib/deepseek-profile-doctor.mjs`)

Read-only, in the same spirit as the V16.5 Reasoning Doctor. It never launches a
browser unless `--probe` was explicitly requested, never mutates a profile and
never prints a credential. Findings carry `ok`/`info`/`warn`/`error`; an `error`
makes the command exit non-zero so scripts can rely on it.

## CLI

```
ues deepseek status [--profile <name>] [--json]
ues deepseek profiles [--json]
ues deepseek doctor [--profile <name>] [--json]
ues deepseek login --profile <name> [--json]
ues deepseek use|switch <name> [--json]
ues deepseek logout [--profile <name>] [--json]
ues deepseek remove-profile <name> [--purge] [--json]
ues deepseek help
```

`status` and `profiles` are read-only and launch **no** browser. `login`
registers the profile and prints the manual instruction; the human signs in
through a live run. `logout` resets the recorded state only — UES never clears
cookies. `remove-profile` drops the record; `--purge` also deletes the browser
directory (whose contents are never read).

## Cache isolation

The consult cache key (`lib/deepseek-consult-cache.mjs`) now includes
`profile:<opaque id>` (or `none`). A consultation answered for one account can
never be replayed for another, even when workspace, diff, packet and question are
byte-identical. A profile-less run keeps its own bucket, so it never reuses a
profiled answer either.

## What V16.7 does NOT do

- No widening of any session/eval/token budget.
- No new persistent store beyond the profile registry metadata.
- No new credential read path of any kind.
- No automatic login, cookie copy, CAPTCHA solve or OTP injection.
- No change to `profileForMode` semantics: it still returns `null` unless a live
  run supplies a name.
