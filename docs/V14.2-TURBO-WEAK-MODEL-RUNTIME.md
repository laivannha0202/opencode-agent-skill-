# V14.2 Turbo Weak-Model Runtime

V14.2 focuses on one goal: make weak and very weak coding models spend less time and fewer tokens on orchestration while preserving UES verification, evidence, safety and high-risk behavior.

It is an optimization layer over V14/V14.1, not a replacement for the existing evidence-gated runtime.

## Design contract

V14.2 MUST NOT gain speed by:

- lowering inherited thinking level;
- removing independent verifier or integration-verifier gates;
- accepting stale verification receipts;
- hiding destructive shell operations;
- dropping raw evidence without a recovery path;
- treating model claims as executable evidence;
- compressing high-risk output lossily by default.

The intended optimization order is:

1. move repeatable decisions into deterministic code;
2. keep child Pi processes warm;
3. shrink context before asking the model to reason;
4. avoid repeated verification when an exact fresh receipt already exists;
5. compact large tool output while preserving recoverable raw bytes;
6. expand context or rerun checks only when evidence requires it.

## 1. Warm Pi RPC workers

The default child runtime mode is `auto`.

UES first attempts a persistent Pi RPC worker. The worker process remains warm across specialist calls, but UES starts a fresh Pi session between runs so repository/model initialization can be reused without carrying the previous specialist conversation forward.

Environment:

~~~text
UES_CHILD_RUNTIME=auto
UES_RPC_MAX_WORKERS=8
~~~

Modes:

- `auto`: prefer RPC, fall back to isolated CLI child if RPC is unavailable;
- `rpc`: require RPC and fail if the worker cannot be used;
- `cli`: always use one-shot child Pi execution.

A worker key includes role, cwd, Pi invocation, model/tool arguments and child compaction settings so incompatible specialist environments are not accidentally reused.

## 2. Interactive steering

When exactly one RPC child is active and Pi receives an interactive steering message, the parent UES extension forwards that message to the child with Pi RPC `steer`.

Messages beginning with stop/cancel/abort or the Vietnamese equivalents `dừng`/`hủy` abort active child workers.

When multiple children are active in parallel, UES deliberately does not broadcast a steering message because there is no deterministic safe target; the message remains available to the parent session.

This complements the hung-tool watchdog. Steering does not pretend that a message can interrupt a shell syscall immediately; known stuck Jest output is detected separately and RPC abort/process-tree cleanup handles the blocked child.

## 3. Unified process supervision

`lib/process-supervisor.mjs` centralizes:

- process-tree termination;
- hard timeout;
- idle timeout;
- stdout/stderr caps;
- abort handling;
- Windows `taskkill /T /F`;
- POSIX process-group termination;
- bounded I/O drain after child exit or kill.

The drain timeout prevents inherited stdout/stderr descriptors held by grandchildren from keeping UES alive indefinitely after the direct child has already exited.

## 4. Rolling hang detection

Tool output is accumulated in a bounded rolling buffer per tool call before matching known hang signatures.

This fixes a subtle stream-boundary failure where:

~~~text
Jest did not exit one second after the
test run has completed.
~~~

could arrive in separate output chunks and evade a detector that only inspected one chunk at a time.

The known Jest open-handle signal receives a short grace period and then the child process tree is terminated if the shell tool remains active.

## 5. Adaptive context budgets

Task Policy retains the existing FAST/STANDARD/DEEP ceilings, but low/medium-risk specialists receive smaller role-aware first-attempt budgets.

Typical targets:

| Profile | Role | First-attempt target |
|---|---|---:|
| FAST | executor | ~6k |
| FAST | verifier | ~4.5k |
| FAST | debugger | ~8k |
| STANDARD | executor | ~11k |
| STANDARD | verifier | ~8k |
| STANDARD | debugger | ~14k |

Failure expands the budget deterministically toward the original policy ceiling.

High-risk tasks keep the original policy budget instead of trading evidence for latency.

Environment:

~~~text
UES_ADAPTIVE_CONTEXT=1
UES_CONTEXT_CACHE_MAX=24
~~~

## 6. Runtime context cache

Context packs are cached by:

- repository cwd;
- workspace fingerprint;
- role;
- runtime budget;
- task text.

A file change changes the workspace fingerprint and invalidates reuse automatically.

Non-Git workspaces fail closed for runtime reuse: the lightweight fingerprint intentionally changes per call instead of pretending a root-path hash proves that files are unchanged.

## 7. Bounded micro-skills

Child Pi still runs with normal skill discovery disabled so the model is not exposed to the entire skill catalog.

UES now selects relevant role/domain skills and compiles a small excerpt containing headings, high-value constraints and verification rules.

Examples:

- executor + payment task -> implementation-engineer + payment-engineering;
- verifier -> test-verification;
- visual-verifier -> visual-fidelity + responsive-verification + browser-qa.

Environment:

~~~text
UES_MICRO_SKILLS=1
~~~

Micro-skills are bounded context, not authority. Repository evidence and explicit task requirements remain stronger.

## 8. Affected-test hints

`lib/affected-tests.mjs` maps changed source files toward likely tests using:

- filename/stem affinity;
- directory proximity;
- path-token overlap;
- bounded content references;
- nearest package test script.

The resolver emits hints and targeted command candidates. It does not claim compiler/LSP-level dependency certainty.

Environment:

~~~text
UES_AFFECTED_TEST_HINTS=1
~~~

## 9. Verification broker

Successful deterministic checks can be reused only when all of the following hold:

- the receipt is PASS;
- command/args match when exact lookup is used;
- a pre-check workspace fingerprint was captured;
- the check itself did not mutate repository state: `workspaceBefore === workspaceAfter`;
- the current workspace still matches that verified state: `workspaceAfter === currentFingerprint`;
- the receipt is within the configured age window.

Receipt reuse therefore fails closed if the check generated or modified tracked/untracked repository content. A successful exit code alone is never enough to make a reusable PASS receipt.

Executor/test tool results are captured at the Pi tool boundary. Verifiers may receive those receipts at the current fingerprint and avoid repeating an identical check when it fully covers the acceptance criterion.

High-risk verifier/integration-verifier runs do not receive this reuse optimization; their independent verification behavior remains conservative.

## 10. Child verification command timeout

The minimal child runtime sets a timeout on test/lint/typecheck/build commands when the model did not supply one.

Default policy targets:

~~~text
FAST      120 seconds
STANDARD  300 seconds
DEEP      600 seconds
HIGH RISK 900 seconds
~~~

The timeout is passed through:

~~~text
UES_CHILD_VERIFICATION_TIMEOUT_SEC
~~~

This is a hang bound, not a forced PASS. Timeout remains a failure signal.

## 11. Full child output recovery

Pi's built-in shell may return a truncated model-visible result and expose `details.fullOutputPath`.

The V14.2 child runtime checks that path and, within a bounded raw-capture size, reads the full output before writing Evidence Store or verification receipts.

Therefore output compaction can preserve more than the already-truncated visible shell text.

Environment:

~~~text
UES_CHILD_TOOL_COMPACTION=1
UES_CHILD_TOOL_OUTPUT_LIMIT=24576
UES_CHILD_RAW_CAPTURE_LIMIT=33554432
~~~

High-risk tasks disable UES child output compaction by default.

## 12. Command-aware reversible compaction

The V14.1 head/signal/tail strategy now has structured reducers for common output classes.

Test output favors:

- PASS/FAIL suite lines;
- assertion failures;
- timeout/open-handle messages;
- stack locations;
- final test totals.

Git output favors:

- diff headers;
- hunk headers;
- conflict/error lines.

The exact captured output remains in Evidence Store.

## 13. Selective evidence retrieval

Evidence references can be read in bounded byte slices as before.

JSON evidence additionally supports selectors:

~~~text
evidence:sha256:<hash>#/errors/0
evidence:sha256:<hash>#foo.bar[0]
~~~

This lets a weak model recover only the required subtree rather than pulling the entire object back into context.

## 14. Dependency-graph context ranking

Context ranking combines semantic seeds with the bounded repository import graph.

The personalized graph rank propagates relevance from:

- semantic query hits;
- explicitly declared files;
- changed files;

through local dependency edges, with weaker reverse edges to surface callers.

This is intentionally described as dependency-graph ranking, not a full compiler/LSP call graph.

## 15. Browser MCP tool minimization

Browser tasks still discover Playwright/Browser MCP capabilities from the Pi host, but V14.2 further reduces the child tool set by task intent.

Examples:

- visual check -> snapshot/screenshot/viewport tools;
- interaction flow -> navigate/click/fill/press/wait;
- diagnostics -> console/network tools.

Ordinary backend tasks continue to receive no browser tools.

## 16. Model-performance confidence

Historical model routing no longer treats a tiny sample as strong enough to reorder weak models.

The routing adjustment now uses a Wilson lower confidence bound and a larger default sample threshold before empirical history changes candidate ordering.

The current default minimum is 8 samples.

## 17. DEEP auto-durable execution

Long-horizon/DEEP structured execution now bridges into `.ues-work/<slug>` instead of merely carrying `durableState: true` as policy metadata.

The controller:

1. initializes durable work;
2. imports the structured plan;
3. records a PASS plan-gate receipt;
4. approves the plan;
5. starts each task with a fenced `runId`;
6. completes a task only after task-level verification and integration into root state;
7. records the final integration gate;
8. finalizes only when the workspace fingerprint matches fresh evidence.

If durable initialization/finalization fails, UES does not silently downgrade the DEEP task to an ordinary non-durable PASS.

## 18. Operational trajectory

The controller emits bounded operational events such as:

- controller.started;
- agent.started;
- agent.completed;
- tool counts/names;
- model tier;
- context budget;
- verifier verdict;
- duration.

Trajectory data records observable runtime state, not hidden chain-of-thought.

## 19. Shell safety by command segment

UES now examines compound command segments separated by bounded parsing of:

- `&&`;
- `||`;
- `;`;
- pipes;
- newlines;

while respecting simple quotes and bracket depth.

A whole-command fallback remains so unsupported nested shell syntax fails closed rather than escaping destructive-command detection.

The minimal child runtime applies the same destructive shell guard, so safety does not depend on the parent extension also being auto-discovered inside a child.

## 20. Benchmark isolation and promotion

Pi baseline evaluation already disables extensions, skills, prompt templates and context files, then explicitly adds only provider extensions.

V14.2 additionally marks a baseline arm invalid if UES controller telemetry appears unexpectedly.

Paired benchmark output now includes two promotion views:

### Strict uplift gate

The existing confidence gate requires statistically supported paired wins and bounded latency/token/context overhead.

### Turbo non-regression gate

The new turbo gate is designed for runtime optimization:

~~~text
quality >= baseline within configured tolerance
AND no suite regression
AND baseline is isolated
AND zero controller false-PASS
AND latency/token/initial-input hard caps pass
AND at least one measured efficiency dimension improves
~~~

This allows a V14.2 optimization to be promoted when correctness is equal but execution is materially cheaper/faster.

## Recommended validation

~~~cmd
npm run syntax
npm test
npm run docs:check
npm run smoke:pi
npm run smoke:package
npm pack --dry-run
~~~

Then run the same weak model in paired mode:

~~~cmd
ues eval-pi --model provider/model --thinking low --suite live --trials 3 --mode both
~~~

For a meaningful promotion decision, increase trials/tasks until the paired sample requirement is met.

## Rollback switches

The major V14.2 optimizations are individually disableable:

~~~text
UES_CHILD_RUNTIME=cli
UES_ADAPTIVE_CONTEXT=0
UES_MICRO_SKILLS=0
UES_AFFECTED_TEST_HINTS=0
UES_CHILD_TOOL_COMPACTION=0
~~~

These switches exist so benchmark regressions can isolate one optimization without removing the quality gates around it.
